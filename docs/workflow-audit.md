## Phase 5 inventory and sales foundation

### Architecture and business rules

The active inventory balance is the `BG Spare Part.stock_qty` field, scoped to a garage and changed by `bike_garage.stock`. Existing `BG Sale` and `BG Job Card` child rows consume this custom balance. `erpnext_integration.py` only validates optional mappings to ERPNext Items, Companies, and Warehouses; no code creates ERPNext Stock Entries, Purchase Receipts, Bin updates, or Stock Ledger Entries. The existing per-garage balance is therefore the operational source of quantity. The new stock movement record is an audit trail for this existing balance, not a competing ERPNext or parallel balance ledger.

The conservative operational rules selected for this implementation are:

- New catalog parts remain at zero. Receiving/adjustment stock changes only through submitted movements; existing Sale and Job Card hooks continue consuming the same `stock_qty` balance.
- Movement types are Purchase Receipt, Positive Adjustment, Negative Adjustment, and Supplier Return. Every movement requires a positive quantity and a reason. Purchase Receipt requires a nonnegative unit cost recorded as receipt information; supplier and purchase reference are plain text because no Supplier or purchase document workflow exists. This is not a payable or accounting posting.
- Positive/negative adjustments require Owner, Manager, or Inventory Manager membership in the active garage. They require a reason. Negative operations cannot reduce on-hand below zero.
- Supplier Return must reference an active submitted receipt for the same garage and part. This first increment permits one full-quantity return per receipt; partial returns are deliberately unsupported. Receipt cancellation is the full reversal operation. It is rejected if the remaining stock cannot support the reversal or if an active supplier return exists; returns must be canceled first.
- Submitted movements are immutable. Frappe cancellation is the audited reversal; it restores the exact quantity effect and fails atomically if that would make stock negative. Customer returns are not enabled because sale cancellation, refund, resale-condition, and accounting rules are undefined.
- Duplicate submissions use a UUID key and normalized-payload fingerprint protected by a database unique index. An exact retry reuses the submitted movement; a conflicting payload is rejected. The part row is locked while a movement is applied. This prevents duplicate requests and serializes competing changes where the database supports row locks; concurrent MariaDB execution remains unverified because staging is unreachable and the isolated suite uses SQLite.
- This phase uses quantity-only inventory. Unit cost is retained as receipt evidence, but no weighted average, FIFO, COGS, or accounting valuation is computed. Legacy balances/costs are not backfilled or treated as verified opening stock. ERPNext stock integration and any valued sale workflow remain blocked until a valuation policy and opening-balance reconciliation are approved.

### Implemented inventory operation

`BG Stock Movement` is a submittable parent record with one part/quantity, garage, type, reason, supplier/reference text, optional original-receipt link, request UUID, payload fingerprint, and before/after snapshots. For this movement workflow, submit and cancel hooks mutate the existing `BG Spare Part.stock_qty`; the stock service locks the part, validates garage ownership and nonnegative result, and updates the movement and balance in the same Frappe transaction. The API stores a fingerprint of the normalized request beside the UUID. An exact retry returns the submitted movement; reuse of a key with a different payload or an incomplete draft is rejected. Submission validates that the fingerprint matches the movement fields, so caller-supplied snapshots or keys cannot turn into an untracked stock change.

Before Phase 7, existing Job Card and Sale hooks applied their own stock deltas but did not create `BG Stock Movement` rows. Phase 7 adds source-linked movement entries for those current deltas without changing the source workflows. The historical importer remains a separate restricted path that preserves reviewed source stock snapshots while suppressing replay of historical Sale/Job Card deltas. No unreviewed audit rows were fabricated for old or existing transactions. Sale creation through Website User resource APIs remains denied.

Movement cancellation requires a reason, stores reversal snapshots, and remains visible with Frappe's cancelled docstatus. A supplier return is one full reversal of one same-garage purchase receipt; the unique original-receipt index prevents another return record. Both return submission and receipt cancellation lock the original receipt before checking its status/returns, so these operations serialize on MariaDB/InnoDB. A receipt cannot be canceled while an active return exists; cancel the return first. Failed submit/cancel operations roll back to a savepoint, including movement state, reasons, snapshots, and stock writes.

The `/stock_receive` website page exposes the operation only to active Owner, Manager, and Inventory Manager memberships. The API derives the garage from the session, rejects forged/cross-garage part and receipt IDs, records costs as non-valued reference data, and uses a UUID unique index for retry safety. Ordinary Website Users have read-only access to movement resources; direct resource creation cannot bypass the authorized API. History is garage-scoped. New catalog creation remains fixed at zero stock and now links to this operation.

### Sales safeguards and remaining lifecycle

New item rates and GST percentages are loaded server-side from the selected part in the same garage, and the existing stock hook applies locked quantity deltas and rejects insufficient stock. Website Users are denied Sale create/write/delete/submit/cancel through Frappe's permission hook while read access for the sales list and invoice remains. ### Payment-ledger proposal (not implemented)

The safe additive model is an append-only `BG Sale Payment` movement linked to one `BG Sale` and its garage. A receipt records a positive amount, date, allowlisted method, optional provider/reference, and unique submission/provider key. A refund/reversal is a separate positive amount linked to the original payment; no payment row is edited or deleted. Net paid is the sum of submitted receipts minus submitted refunds, outstanding is max(total minus net paid, zero), and Sale payment status is derived as Pending/Partially Paid/Paid. Overpayment is rejected. Cancelling a receipt requires a compensating reversal and authorization; refunds cannot exceed the unreversed original payment or net paid. These are proposals for an operational ledger only and do not create ERPNext Payment Entries or accounting postings.

Before implementing that schema, the business owner must confirm which methods require provider evidence, whether refunds can be partial and who authorizes them, whether overpayment is always prohibited, rounding/currency precision, treatment of disputed/chargeback payments, and how legacy sale statuses are reconciled. No historical amount will be synthesized. Legacy records without reliable payment evidence must be tagged/reconciled separately before derived status replaces their current display. The schema should use database uniqueness for request/provider IDs and preserve audit rows through append-only cancellation/reversal events.

## Phase 7 stock movement audit coverage

### Lifecycle semantics and implementation

`BG Sale` and `BG Job Card` continue using the existing `BG Spare Part.stock_qty` balance and `_apply_stock_changes` helper. The helper locks each affected part, derives before/after quantities from the locked row, validates nonnegative stock and garage ownership, then writes stock and source-linked `BG Stock Movement` records in the same savepoint and caller transaction. If either write fails, the savepoint rolls back both. Movement rows are internal records created in a private source-audit context; ordinary inventory APIs and direct document inserts cannot provide source references or caller-authored balances. Source-linked movements cannot be independently reversed: the source workflow records the actual inverse delta.

- **Sale:** `on_update` compares the persisted document before-save item quantities with the current items. New/increased consumption decreases stock (`Sale Consumption`); reduced/removed quantities increase stock (`Sale Restoration`). Each nonzero part delta has one movement with source event `Updated`, including initial creation. A no-op save writes none. Existing Sale is not a submittable/cancelable lifecycle; deletion restores its currently consumed items and records `Deleted` restoration before the parent is removed. Repeated deletion cannot repeat after deletion; retrying a failed request relies on the enclosing Frappe transaction rollback. The existing Sale delete policy remains unchanged.
- **Job Card:** `on_update` consumes the active card's part rows and diffs edits against the prior saved state. Active-to-`Cancelled` restores the previous consumption (`Cancelled`); repeated saves while canceled produce no delta. `Cancelled`-to-active consumes current rows (`Reactivated`). Deleting an active card restores its current consumption with `Deleted`; deleting a canceled card changes no stock and creates no movement. Repeated unchanged saves and repeated cancellation states produce no duplicate movement.
- **Validation and commit boundary:** invalid quantities, wrong-garage parts, and insufficient stock fail before stock writes. The source document update, stock balance, and movement rows share the same request transaction; an uncaught hook/audit error fails the source operation. The helper savepoint also protects against a caller catching a later stock or movement write error. These transaction guarantees were exercised on SQLite; actual concurrent MariaDB behavior was not run.
- **Movement details:** one row per changed part/delta; sign is represented by consumption/restoration type and `qty` is the positive absolute delta. `stock_before` and `stock_after` are server-derived from locked stock. Garage comes from the saved source document and is checked against each part and the source reference. A blank first Select option prevents unrelated inventory movements from receiving an implicit `BG Sale` source type.

This adds movement coverage for current Sale and Job Card stock mutations, alongside the existing receipt, adjustment, supplier-return, and their cancellation/reversal movements. Historical import still suppresses replayed source deltas. No legacy movements were synthesized: existing history remains incomplete before this implementation and current balances are not evidence of historical source deltas. Operations that produce zero stock change, including no-op edits and deletion of a canceled Job Card, correctly create no movement.

## Phase 8 payment-ledger design decisions

Before Phase 8, the existing `BG Sale.payment_status` and `payment_mode` were only legacy summary/input fields, with no paid-amount field or payment transaction records; old `Paid` and `Partially Paid` values therefore did not establish an amount received. The operational sale total is `grand_total`, derived from item amounts, tax, and labor. Payment mode alone is not evidence. ERPNext mapping is reference-only and creates no accounting entries.

The additive model is a separate append-only `BG Sale Payment` receipt record linked to one Sale and its server-verified garage. It stores a positive amount, allowlisted method, optional reference, server owner/creation time, unique retry key, and payload fingerprint. Amounts use Frappe's configured Currency precision and rounding method for `BG Sale.grand_total`; overpayments are rejected, so outstanding cannot be negative. Each receipt locks its Sale before checking existing requests and the cumulative ledger total. Exact retries return the existing receipt; changed payloads on a reused key fail. Only Owner, Manager, and Accountant memberships can read or record payments; sale creation remains disabled for Website Users.

New operational Sales are marked `Tracked` with an initial paid amount of zero. Legacy imports preserve their source status and payment mode but are marked `Unverified` with no inferred paid amount. Existing Sales remain `Unverified`; their status and historical fields are not bulk-edited, no payment is inferred from `Paid`, and payments cannot be added until the legacy Sale receives an explicit future reconciliation decision. For tracked Sales, paid amount and `Pending`/`Partially Paid`/`Paid` status are derived from receipt records and are protected from caller writes. A sale total cannot be reduced below recorded receipts. Any Sale with receipts is protected from deletion, and BG Sale has no cancellation lifecycle. Refunds/reversals are not exposed in this increment because refund authorization, partial-refund rules, and external-payment evidence have not been decided; receipts are immutable and cannot be canceled/deleted. No stock movement, Sale, or ERPNext accounting entry is created by payment recording.

### Implemented receipt operation and compatibility

`BG Sale Payment` is a new read-only resource DocType. Receipt creation and history retrieval use garage-scoped whitelisted APIs; the create endpoint accepts only Sale, amount, payment method, optional reference and retry key. Garage ownership is derived from the active membership, the Sale is scoped before loading, and the linked Sale and Payment rows are checked for the same garage. Owner, Manager and Accountant memberships may record/read receipt details; other members cannot access the ledger. Resource writes and forged payment rows are rejected by permissions and the DocType controller. A global unique retry key plus payload fingerprint makes duplicate requests idempotent and rejects changed payload reuse.

The API locks the Sale before checking its current ledger and balance, then performs a locking read of receipt rows on MariaDB. A savepoint includes the receipt insert and Sale summary update. `amount_paid` and `payment_status` are recalculated from ledger rows, and a caller cannot edit either summary field directly. Frappe's configured Currency precision and rounding policy are applied before balance validation. UI totals and reports now use verified ledger amounts; daily collection-by-method and monthly collection summaries use payment creation time. Legacy Sale statuses render as Unverified, are excluded from collection totals, and their outstanding values are not guessed. No payment-entry UI was added because an operator has no approved refund/reversal path to correct an erroneous receipt; the authorized API is the only receipt workflow in this phase.

`BG Sale` is not submittable and has no cancel event. Its deletion hook checks for ledger receipts before the stock restoration hook; Sales with receipts cannot be deleted. Sale total edits that would fall below recorded payments are rejected. Refund, reversal, chargeback, payment cancellation, and legacy reconciliation endpoints are not implemented. No refunds, reversals, or historical payments were fabricated. New Sale creation remains disabled for Website Users, and this work does not enable it.

The isolated test site received targeted `frappe.reload_doc` syncs for `BG Sale` and the new `BG Sale Payment` DocType only. The expected schema impact is two read-only summary columns on `BG Sale` (`amount_paid` nullable; ledger status defaulting to `Unverified`), one new indexed InnoDB receipt table, and its unique retry-key index. Existing `payment_status`, `payment_mode`, Sale rows, and business records were not bulk-updated.
